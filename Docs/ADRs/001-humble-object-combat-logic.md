# 001: 결정론적 전투 시스템 구현을 위해 험블 오브젝트 패턴을 적용함

## 상태 (Status)
- 승인됨 (2026-10-14)

## 맥락 (Context)
우리는 God of War 스타일의 묵직한 액션 근접 전투 시스템을 개발하고 있으며, 기획서(`Docs/GDD.md`)는 다음 세 가지 핵심 엔지니어링 조건을 요구한다:

1. **프레임 단위의 정확성과 결정론 (GDD 1.2)**:
   공격의 생명주기(Windup / Active / Recovery)와 선입력 버퍼는 60 FPS 기준으로 정밀하게 제어되어야 한다. 가변 프레임 환경에서도 동일한 입력 시퀀스에는 항상 동일한 판정과 상태 전이가 오차 없이 발생해야 한다.
2. **독립 검증과 빠른 테스트 주기 (GDD 1.2)**:
   전투 규칙은 씬 로딩, 렌더링, 물리 시뮬레이션 같은 무거운 엔진 환경 없이도 모듈 단위로 독립 실행되어 밀리초 단위로 자동 검증(Zero-GC 무할당 포함)될 수 있어야 한다.
3. **캐릭터별 독립된 시간 제어 (GDD 2장, 4.3절, 4.1절 NOTE)**:
   타격 적중 시 칼날의 저항감을 주는 비대칭 히트스탑은 공격자와 피격자에게 서로 다른 길이의 시간 정지를 부여해야 한다. 유니티의 전역 `Time.timeScale`은 씬 전체의 시간을 멈추므로 개별 엔티티의 차등 정지를 표현할 수 없다.

이 요구들을 종합하면 **"전투 규칙은 유니티 엔진 없이 순수 코드로 실행되어야 하며, 시간은 엔진이 아닌 외부에서 주입받아야 한다"**는 결론에 이른다.

## 결정 (Decision)
우리는 전투 시스템에 **험블 오브젝트(Humble Object) 패턴**을 적용하기로 결정했다.

1. **순수 로직 격리 (`CombatSystem.Core`)**:
   전투 상태와 규칙(단계 전이, 프레임 윈도우, 조작 권한, 선입력, 히트스탑 타이머, 데미지, 넉백)은 `UnityEngine`을 일절 참조하지 않는 순수 C# 어셈블리로 분리한다 (`noEngineReferences: true`).
2. **어댑터의 험블화 (`CombatSystem`)**:
   `MonoBehaviour` 컴포넌트들은 계산을 하지 않고, 유니티 엔진과 순수 로직 사이에서 입출력(입력 전달, 애니메이터 포즈 동기화, CharacterController 물리 이동)을 중계하는 얇은 어댑터 역할만 수행한다. Input System은 어댑터만 참조한다.
3. **시간 주입 (Time Injection)**:
   로직은 `Time.deltaTime`을 직접 읽지 않고, 외부에서 `Tick(float dt)` 형태로 시간 경과를 주입받아 프레임과 독립 시간 정지를 완벽히 제어한다.
4. **애니메이터 역할 재정의**:
   Animator Controller는 규칙을 갖지 않고, 순수 로직의 진행 상태를 시각적 포즈로 표현하기만 한다.
5. **어셈블리 경계 강제**:
   컴파일러 레벨에서 엔진 참조가 원천 차단되는 `CombatSystem.Core` asmdef를 통해 이 경계를 엄격히 강제한다 (`AGENTS.md` §3 참조).

## 대안 (Alternatives)
### MonoBehaviour에 전투 규칙을 구현하는 일반적인 유니티 개발 방식
전투 상태와 규칙을 `MonoBehaviour` 컴포넌트(`Update`, `Time.deltaTime`)에 직접 작성하고, 필요 시 PlayMode 테스트나 에셋을 활용해 검증하는 전형적인 유니티 개발 방식이다.

- **선택하지 않은 이유**:
  - **결정론 통제 및 프레임 경계 검증의 어려움**: 테스트 환경에서 시간을 프레임 단위로 제어할 수 없어, 60 FPS 기준의 프레임 경계 규칙(Windup / Active / Recovery)을 정밀하게 검증하기 어렵다.
  - **독립 시간 축 구현의 한계**: `Time.deltaTime`과 유니티 전역 시간에 종속되어 있어, 캐릭터별로 서로 다른 시간 정지를 부여하는 비대칭 히트스탑을 구현하기 어렵다.
  - **느린 검증 주기와 테스트 결합도**: 씬 로딩과 플레이모드 진입이 필요해 테스트 실행 주기가 길어지고(초~수십 초), 순수 로직의 가비지 무할당(Zero-GC) 검증이 어렵다.

## 결과 (Consequences)
### 1. 구조적 변화
- **모듈 분리**: 모든 전투 모듈은 순수 로직과 Unity 어댑터 두 부분으로 나뉜다. 로직은 `CombatSystem.Core`에, 어댑터는 `CombatSystem`에 위치한다.
- **애니메이터 제어권 이전**: 전투 상태(Combat State)는 순수 로직이 소유하며, 애니메이터(Animator)는 그 상태를 따라 시각적 포즈로 표현만 한다. Animator Controller 내부에는 어떠한 전이 규칙도 두지 않는다.
- **수평 이동(XZ 평면)과 수직 물리 분리**: 로직 어셈블리는 `UnityEngine` 타입을 쓸 수 없으므로, 캐릭터의 바닥 이동(전후/좌우 XZ 평면)과 회전 각도만 `System.Numerics.Vector2`로 계산한다. 높이 및 수직 방향 물리(중력, 접지 판정)는 Unity 어댑터가 전담한다.

### 2. 트레이드오프 (Trade-offs)
- **파일 수 증가**: 모듈마다 순수 로직 클래스와 어댑터 클래스로 나뉘어 관리할 파일 수가 늘어난다.
- **인스펙터(Inspector) 시각화 부재**: 실행 중 순수 로직의 상태가 Unity 인스펙터에 기본으로 보이지 않는다. (필요 시 어댑터가 읽기 전용 프로퍼티로 노출한다.)
- **경계 데이터 변환 비용**: 로직과 어댑터의 경계에서 데이터 타입 변환(`System.Numerics` ↔ `UnityEngine`) 비용과 코드가 소량 발생한다.
